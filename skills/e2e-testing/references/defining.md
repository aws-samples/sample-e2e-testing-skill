# 調査と定義(defining)

シナリオ候補は、実アプリを操作して観測したことと参考資料だけを根拠に書く。

## 0. 参考資料の確認

調査を始める前に、ユーザーに次を聞く:

> シナリオ作成の参考にできるものはありますか?(仕様書・設計書・要件チケット・ソースコード・既存の手動テスト手順など)

- ある: 読んで要件文とシナリオ候補の根拠にし、候補に出典を付ける(形式は [conventions.md](conventions.md) の「Gherkin 規約」の引用元)
- ない: 実アプリの探索だけを根拠にし、引用元は書かない

## 1. 初回のみ: 全体調査と機能マップ

`features/feature-map.json` が無いときだけ行う。

1. `npm run e2e:reset-data` でベースライン状態にする。ベースラインに代表データが無ければ、[setup.md](setup.md) の「2. ユーザーへの質問」3 に戻って含め方をユーザーと決める
2. 既定ロールの seed に attach し([setup.md](setup.md) の「seed への attach 定型」)、主要な画面・ナビゲーション・操作を一巡する。ロールが複数あれば、他のロールの seed でも一巡してロールによる違いを洗い出す
3. 参考資料があれば突き合わせ、資料にあって画面に無い機能と、画面にあって資料に無い機能を洗い出す
4. 探索が終わったら、バックグラウンドのテストを止める
5. 機能の案、候補、確認したいことを `features/feature-map.json` に書き([conventions.md](conventions.md) の「feature-map.json の形式」。全機能 `未着手`。欄の書き方は下の「feature-map の欄の書き方」)、ビューアをビルドする(SKILL.md の「表とレビュー用 CSV の更新」)
6. チャットには、変わった点と質問だけを書く。機能の一覧は `features/viewer/index.html` で見てもらう
7. 答えを feature-map に反映する(候補を機能に移す、答えの出た `questions` の項目を消して `decided` に書く、着手順に並べ替える、など)。反映したらビルドし直して 6 に戻る
8. 確認したいことと候補が無くなり、ユーザーが一覧を確定したら、機能ラウンドに進む

### feature-map の欄の書き方

読み手は、技術に詳しくない意思決定者を想定する。`summary`、`includes`、`excludes` は画面と操作の言葉で書き、コードの名前で書かない。

- `summary`: 利用者から見て何ができる機能かを 1〜2 文で
- `includes`: 含む画面、操作、ロール
- `excludes`: 含まないもの。隣の機能に入れたものは、その機能の名前も書く
- `sources`: 参考資料の箇所と、探索で確かめた画面
- `questions`: ユーザーに判断してほしい点
- `decided`: ユーザーが決めたこと。日付と理由を付ける

機能ラウンドで機能を見直すときも、これらの欄を最新にする。

## 2. 機能ラウンド

feature-map の順に、1 機能ずつ 2.1〜2.4 を行う。

### 2.1 探索

seed に attach して対象機能を実際に操作する。ロールで挙動が変わる箇所は、そのロールの seed に attach し直して確かめる。ログイン・ログアウトなど認証そのものを調べるときは「未認証」の seed に attach する。attach した後にログアウトするなどして状態を変えてよい(seed から始めるのは、テストと同じ実行条件で観察するため)。

### 2.2 採番

候補を書く前に行う。

1. `npm run e2e:trace` を実行し、標準出力の `要件番号の最大値: REQ-xxx` を読む
2. 新しい要件番号を最大値 + 1 から連番で振る(`なし` なら `REQ-001` から)。枝番は要件ごとに 1 から振る。.feature を目で数えて採番しない

### 2.3 候補の提示

次の形式で、要件ごとにまとめて示す。1 つの要件(Rule)の下に、それを検証するシナリオを並べる。

```markdown
## 機能「<機能名>」の要件案とシナリオ候補

### 候補(要件文・シナリオとも、採用・修正・却下を判断してください)

REQ-004(案) WHEN 検索欄にキーワードを入力して検索した, the 会員サイト SHALL 商品名にキーワードを含む商品だけを表示する
  引用元: docs/spec.md > 4.1 商品検索
  REQ-004-1(案) キーワードに一致する商品だけが表示される(正常系)
    Given <...> / When <...> / Then <...>
  REQ-004-2(案) 一致する商品が無いときはメッセージが表示される(異常系)
    Given <...> / When <...>

### 疑問点(回答が必要です)

Q1. [REQ-004 要件文] 「商品名に」はカテゴリ名も含みますか
Q2. [REQ-004-1] 部分一致ですか、前方一致ですか
Q3. [REQ-004-2] 一致する商品が無いときに表示される文言(探索では確認できませんでした)
```

- `(案)` はチャット上だけの表記で、.feature には書かない。引用元の行は出典があるときだけ書く。疑問点には、どの要件文・シナリオへの質問かを `[ID]` で付ける
- 要件文は [conventions.md](conventions.md) の「Gherkin 規約」の EARS 形式で書く。探索と参考資料のどちらにも無いことは書かない。意図・範囲・条件(対象範囲、ロールによる違い、任意機能かどうかなど)が確かめられなければ、要件文への疑問点にする
- 探索で観測できた完了条件(画面遷移、表示文言、要素の出現)は Then まで書く。観測できなかった、または判断が要る完了条件(エラー時の期待挙動、境界値でどうあるべきか、仕様の意図)は Then を書かずに疑問点にする
- 1 つの要件文に SHALL が 2 つ以上あれば、要件を分ける
- 候補が 10 を大きく超えるなら、機能の分割を提案する

### 2.4 ユーザー判断と .feature の確定

ユーザーが候補を取捨・編集・追加し、疑問点に答える。

- シナリオへの疑問点に「今は決めない」と答えた: そのシナリオを候補から外す
- 要件文への疑問点が未回答: その .feature の確定を保留し、回答を求める
- 要件文への疑問点に「今は決めない」と答えた: その要件と配下のシナリオをまとめて外す
- 編集で要件が増えたら、提示済みの最大番号の続きを振る。減っても残りの番号は振り直さない

確定したら:

1. `features/<機能スラッグ>.feature` に、[conventions.md](conventions.md) の「Gherkin 規約」どおりに書き出す
2. `npm run e2e:trace` を実行し、`## 不整合` に対象機能の `ID 未付与` と `重複 ID` が無いことを確かめる(`未生成` はテスト生成前なので出てよい)
3. feature-map の状態を `定義済み` にする
