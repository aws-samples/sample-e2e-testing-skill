# E2E テスト(e2e-testing)

このスキルでの E2E テストは、利用者がブラウザで行う一連の業務の操作を、画面から始めて結果が画面に表れるまで通して確かめるテスト。テスト対象のアプリは、画面からデータベースなどの永続化層まで本物の構成要素をつないだ、本番相当の検証環境で動かす。テストは利用者と同じようにブラウザの画面を操作し、画面に表れた結果で合否を判断する。バックエンドとつながない画面部品のテスト、画面を通さない API だけのテスト、性能と使いやすさの評価は扱わない。

.feature(Gherkin)は、テスト生成 → 実行 → 結果確認を繰り返して検証し続ける仕様として扱う。実行結果と食い違えば書き換えるが、書き換えるかどうかはユーザーが決める。

## 規約ダイジェスト

要件・シナリオ・テストコード・実行結果は ID でつなぐ。要件は .feature の `Rule:` に要件 ID 付きで書き、シナリオとテストにはシナリオ ID をそのまま書く(形式は [conventions.md](references/conventions.md))。対応の有無と不整合の有無は、照合ツール `scripts/e2e-trace.mts` の標準出力と終了コードだけで判断する。ファイル名やシナリオ名が似ていることや推測で補わない。`features/last-run.json`(照合ツールが書く全体実行の結果の控え)と `features/viewer/`(ビューアの出力)は生成物なので、手で編集しない。

## 前提条件

作業の最初に次を確かめる。確認と導入のコマンドは [setup.md](references/setup.md) の「1. 前提条件とワークスペースの確認」にある。Windows(PowerShell)で実行するときのコマンドの読み替えも、その節にある。

- playwright-cli スキルが使えること。ブラウザ操作、テストのデバッグ実行(`--debug=cli` / attach)、コード生成は playwright-cli スキルの手順で行い、本スキルには書かない
- playwright-cli コマンドが動くこと
- Node.js 22.18 以上であること(照合ツールを型ストリップで直接実行し、表とレビュー用 CSV のビルドにも使うため)

欠けていれば作業を始めず、導入を案内して待つ。Node.js が古い場合も更新を待ち、`--experimental-strip-types` で回避しない。

## 照合ツールの版の確認

作業の最初に、プロジェクトの `scripts/e2e-trace.mts` と、このスキルのディレクトリの `scripts/e2e-trace.mts` の版を比べる。版は、ファイルの中の `export const TRACE_TOOL_VERSION = <整数>;` の行の整数。このスキルのディレクトリは、このスキルを読み込んだ場所(`viewer/build.mjs` を実行するときと同じ)。プロジェクトに `scripts/e2e-trace.mts` がまだ無いとき(setup の前)は比べない。

- プロジェクトのコピーが古い: ユーザーに確認せずにスキルの `scripts/e2e-trace.mts` をコピーし直し、そのことを報告に書く
- 版が同じなのに、改行を LF にそろえて比べた中身が違う: プロジェクトで手が入っている。上書きしてよいかユーザーに聞く
- プロジェクトのコピーで版の行が読めない: 上書きしてよいかユーザーに聞く
- プロジェクトのコピーのほうが新しい: コピーしない。スキルを更新するよう報告に書く

「E2E テストをやりたい」「次は何をすればいい?」のような漠然とした依頼では、`features/feature-map.json` の有無と内容から現在地を判断し、次の段階を提案する。feature-map が無ければ setup → defining の初回調査から始める。

## 機能ループ

全機能を工程ごとにまとめて進めず、1 機能ずつ最後まで通す:

```
feature-map の順に機能を 1 つ選ぶ
  → defining: 探索 → 要件案(Rule)とシナリオ候補(ID 案付き)と疑問点を提示
  → ユーザーが候補を取捨・編集し、.feature を確定する
  → generating: シナリオごとにテストを生成して実行
  → 食い違いは「失敗と不整合の扱い」に従う
  → 全シナリオ green、照合ツール(npm run e2e:trace)で対象機能の不整合 0
  → feature-map を テスト済み にして次の機能へ
```

機能を 1 つ終えたら generating.md「機能の締め」の報告をし、ターンを終えずに次の機能の探索に進む。ターンを終えてユーザーを待つのは、.feature の候補や修正案を提示したとき、アプリのバグ疑いを質問したとき、各 reference でユーザーへの質問・依頼が求められているとき、全機能が `テスト済み` か `対象外` になったときだけ。

アプリを操作する作業(データ初期化、探索、seed への attach、テストの実行)は 1 つずつ行い、サブエージェントに並列で任せない。テストデータとブラウザを共有するので、並列にすると偽の失敗や、別の作業の操作が混ざった観察になる。サブエージェントに任せてよいのは、ソースコードや参考資料を読むだけの調査。

## 表とレビュー用 CSV の更新

以下のときは、ユーザーへ次に報告する前に(ターンを終える前を含む)、頼まれていなくても、プロジェクトのルートでビューアをビルドする。同じターンに何度書き換えたときも、報告の前に 1 回でよい。

- `features/feature-map.json` か `.feature` を書き換えたとき
- 全体実行で `features/last-run.json` を書いた後

```bash
node <このスキルのディレクトリ>/viewer/build.mjs
```

出力は `features/viewer/` の、要件とシナリオの表(`index.html`)と、行ごとにコメント欄を持つレビュー用の CSV(`review.csv`)。エージェントがコミットするときは、書き換えた元のファイルとビューアの出力を同じコミットに入れる。ビルドが失敗したら、エラーの中身で下の「失敗と不整合の扱い」に振り分ける。エラーの読み方と、報告に添えることは [viewer/README.md](viewer/README.md) に従う。

## ユーザーが判断すること

### .feature の確定と変更

要件文(`Rule:`)とシナリオは、新規でも書き換えでも、候補(修正案)と疑問点を提示し、ユーザーの判断を得てから .feature に書く。**疑問点(要件文へのものを含む)が未回答のうちは確定しない。**

### 失敗と不整合の扱い

テストの失敗、実演中の食い違い、照合ツールの不整合は、次の 3 つに分けて扱う。

- テストコードの問題(ロケータ drift、アサーションの取り方、待ち方): .feature の意味は変わらないので、ユーザーに確認せずに直してよい
- .feature の誤り: アプリは意図どおり動いていて、シナリオの記述が古い・誤っているという仮説。停止し、変更前 / 変更後の句を示した修正案を提示する。承認されてから .feature とテストを直す
- アプリのバグ疑い: .feature は正しく、アプリの挙動がおかしいという仮説。停止して質問する。ユーザーがバグと確定したら、[conventions.md](references/conventions.md) の「既知バグ」の書き方で記録する

.feature の誤りとアプリのバグ疑いを提示するときは、シナリオ名、期待した挙動(該当する Then 句)、観測した挙動(snapshot の抜粋など)、どちらだと考えたかとその根拠を含める。迷ったら両方の仮説を書く。

照合ツールの不整合は、[conventions.md](references/conventions.md) の「不整合の種類」の種別ごとに次のように扱う:

- テストコードの問題として直し、照合ツールを再実行する: 孤立テスト、ID 不一致、原因がテスト側の不明 ID 参照、原因がテストファイル側の重複 ID
- エージェントが直し、照合ツールを再実行する: `feature-map の形式` のうち、JSON の書き方の誤り(末尾のカンマなど)。中身を変えない直しに限る
- .feature の誤りとして修正案を提示し、判断を待つ: 原因が .feature 側の重複 ID、ID 未付与、未生成の要件の扱い、原因が .feature 側の不明 ID 参照
- 修正案を示し、判断を待つ: そのほかの `feature-map の形式`、`feature-map に無い .feature`、`.feature の無い機能`、`slug の重なり`

不整合が残る間、feature-map の状態は `定義済み` のままにする。
